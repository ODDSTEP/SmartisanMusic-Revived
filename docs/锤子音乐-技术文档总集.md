# 第一部分 · 项目架构总览

更新日期：2026-09-07。应用 UI 已完整使用 Jetpack Compose；当前视觉基线来自迁移前经过校准的实现。工程保持单 `:app` 模块，源码根包为 `com.smartisan.music`，applicationId 为 `app.smartisanmusic.revived`。迁移范围、验证状态与待验收项见 [Compose 迁移记录](compose-migration.md)。

## 状态与系统边界

[MainActivity](../app/src/main/java/com/smartisan/music/MainActivity.kt) 负责窗口、权限、外部音频入口和 Compose 宿主。[MusicAppShell](../app/src/main/java/com/smartisan/music/ui/shell/MusicAppShell.kt) 协调目的地、编辑态、页面栈及覆盖层。具体页面消费已有媒体与设置状态，通过回调或 controller 发送用户意图。

| 所有者 | 职责 | UI 的接入方式 |
| --- | --- | --- |
| [playback](../app/src/main/java/com/smartisan/music/playback/) | Media3 服务、队列、播放位置、会话恢复、音频与歌词解析 | 使用现有 Player/controller 和 session command；页面不创建第二个播放器 |
| [data](../app/src/main/java/com/smartisan/music/data/) | Room、DataStore、资料库索引、收藏、播放列表和设置 | 订阅已有 Repository / Flow，写入仍经原业务入口 |
| [launcher](../app/src/main/java/com/smartisan/music/launcher/) | 应用图标 alias 切换 | 以系统组件状态确认选择，不另存一份图标状态 |
| [ui/library](../app/src/main/java/com/smartisan/music/ui/library/) | 资料库 UI state、共用列表和专辑展示 | 将已有媒体映射为页面数据，不维护第二套媒体索引 |
| [ui/shell](../app/src/main/java/com/smartisan/music/ui/shell/) | 全局页面编排、Tab、标题栈、播放条和跨页面覆盖层 | 持有导航与临时编辑状态，转发页面事件 |

Room schema、DataStore key、稳定媒体 ID、队列顺序、当前项及恢复协议不因 UI 迁移而改变。删除媒体继续通过系统授权协调器执行；确认界面只表达用户意图，授权结果仍走原有链路。

## 图形、交互与生命周期

2026-09-07 调整：专辑与艺术家采用 `SharedTransitionLayout` / `sharedBounds`，网格封面依次显现，切回列表时以稳定条目 ID 匹配封面并缩放落位。浏览锚点在目标布局显示前定位，中途反向沿已测量边界继续。播放列表与队列拖拽的让位、取消和落位继续使用 Compose 动画，数据顺序仍由原回调提交。

布局、列表、弹层和交互节点由 Compose 构建。原有 `res/layout`、UI View 子类、adapter 和 framework shim 已移除；`drawable` / `color` XML 是图形资源，继续保留。[attrs.xml](../app/src/main/res/values/attrs.xml) 中的 `SmartisanScrollbar` 仅声明系统滚动条主题属性，由 AAPT 生成正确的索引顺序，不承载 View 布局。页面使用自定义 Smartisan 组件呈现现有视觉。

[SmartisanDrawablePainter](../app/src/main/java/com/smartisan/music/ui/components/SmartisanDrawablePainter.kt) 保留 selector、ColorStateList、9-patch、配置变体及 Drawable 回调生命周期。`smartisanTextSize` 按资源解析后的像素转换字号，正文明确设置 font padding。[SmartisanTitleText](../app/src/main/java/com/smartisan/music/ui/components/SmartisanTitleText.kt) 使用公开 TextPaint 和文字布局 API 维持伪粗体及基线。

背景统一使用 [smartisanPainterBackground](../app/src/main/java/com/smartisan/music/ui/components/SmartisanPainterBackground.kt) 在 `drawBehind` 中按已测量尺寸绘制。`Modifier.paint` 即使关闭固有尺寸仍会改变父约束，不能用于自适应高度的底栏、列表或弹层背景。装饰阴影显式声明资源高度，不通过图片宽度缩放决定容器高度。

[SmartisanPressFeedback](../app/src/main/java/com/smartisan/music/ui/components/SmartisanPressFeedback.kt) 统一收集点击控件的按压交互，让同帧结束的快点也能显示原有 selector 或按压位图。背景、文字和图标共享该视觉状态；取消立即清除，正常释放使用公开平台反馈时长。它不延迟业务回调，不代替拖拽、滑块、开关或导航的状态机。列表蓝底上的文字白色反馈与普通、多选、播放态分开处理，核对范围见 [列表选中样式](list-selection.md)。

Compose 绘制阶段仍可调用 Android 的公开 `Canvas` / `Drawable` / `TextPaint`；[睡眠定时滚轮](../app/src/main/java/com/smartisan/music/ui/playback/PlaybackSleepTimerPicker.kt) 使用 Compose `AnimationState`、Android 样条衰减和吸附动画，不再依赖 `Scroller` 的墙钟时间。系统窗口、点击音、触觉及权限桥接仍使用适用的公开平台 API。UI 测试中的原生标题栏和 Drawable View 只用于对照，不进入生产页面。

普通层级返回统一使用 [SmartisanNavigationMotion](../app/src/main/java/com/smartisan/music/ui/navigation/SmartisanNavigationMotion.kt)，同一套 300ms 时序驱动页面和标题各槽位。[SmartisanPageStack](../app/src/main/java/com/smartisan/music/ui/navigation/SmartisanPageStack.kt) 提供固定标题区与整宽内容区，供分离标题的层级页复用；已有标题与内容分离的专辑、艺术家、文件夹、流派和播放列表分别复用 `TitleBarTransition` 与 `PageStackTransition`。标题图标使用继承的局部动效状态，嵌套标题不会覆盖父级淡出。页面业务与存储不归动效组件所有。

AndroidX `BackHandler` 仅处理已确认的返回，与标题返回按钮汇入同一页面状态；Manifest 关闭系统预测性返回动画，生产 UI 已移除预测进度、消费标记与相关参数。设置/播放/搜索整页覆盖层使用纵向展开收起，区别于层级页的横向返回。复用方式、便签参考及测试边界见 [统一导航动效](navigation-motion.md)。

列表使用稳定项键和独立滚动状态。按压、编辑、滑删、滑选和拖拽各有明确手势所有者；边缘自动滚动跳过不可选择的标题/页脚。隐藏页面不应接受点击或暴露重复的可访问节点。动画和后台工作绑定 Composition 生命周期，不能为离开的页面留下运行中的任务或 Drawable 回调。

多选行通过 `editMode && selected`（或 checked）映射 Drawable 的 activated 状态，`listview_selector` 统一读取日间/夜间的 `list_selection_background`。按下、焦点与多选使用不同优先级，当前播放状态不映射为多选蓝底。范围与设计依据见 [列表选中样式](list-selection.md)。

封面加载沿用原 LRU：已有缓存可先显示，同一加载器内相同请求合并，媒体解析和解码在 IO 线程执行；离开页面取消所属任务。列表、队列和转场复用加载入口，不复制解码流程。主题资源仍通过 `values-night` / `drawable-night` 提供，[夜间资源生成脚本](../tools/generate_night_drawables.py) 维护对应输入和输出。

专辑封面预览由 `GalleryArtworkMotion` 驱动直线缩放、轻微回弹和背景透明度；几何计算保留原始图片比例与缩略图裁剪。`AlbumArtworkBrowserHost` 在应用同一窗口顶层绘制，来源页只提交请求并持有来源标识；移除来源页时取消对应预览。缩回完成时先恢复缩略图、再移除预览，避免跨窗口交接出现空帧。参数依据和验证边界见 [封面预览动画](gallery-artwork-motion.md)。

## 后续维护规则

- 新页面放入最窄的功能包；跨页面共用的视觉或手势组件才放入 `ui/components`。避免将页面细节再次堆回 `MusicAppShell`。
- UI 只保留渲染、临时交互和事件协调。播放、媒体扫描、收藏、设置和持久化继续由现有业务层拥有。
- 新类型默认 `private`，有跨文件调用再使用 `internal`；不为拆文件引入新的模块或状态源。
- 视觉调整以已校准实现、既有资源和设备反馈为依据，保留尺寸、时序、按压、触摸和字体语义。原版没有的能力延续相邻页面的视觉语言。
- 删除资源时同时检查 main/test/androidTest、Manifest、全部配置下的 XML 依赖及生成脚本；不要只根据文件名或单次 Lint 报告判断。
- 验证按风险选择；自动构建与设备验收分别记录。完整清单见 [迁移记录](compose-migration.md#验证与待验收)。

设置入口通过 `SmartisanFullScreenTransition` 让标题与正文整体移动，内部二级页再使用固定标题转场。主壳的“更多”溢出目的地通过 `ProjectedNavigationTitle` 注册已有标题，保留页面原处高度、在主壳顶层绘制同一个实时标题槽位；不复制页面、状态或资源解码。渲染槽位独立重组，注册以所有者标识清理，避免退场页面清掉新页面标题。全屏设置与播放列表添加模式停用外层固定标题。

设置退出恢复主壳时，标题槽位保持注册，仅切换原处/顶层渲染。底栏通过 `retainedChromeVisibility` 暂停放置与子级无障碍暴露，保留播放条的组合和动画状态；避免尾帧重新挂载造成标题空白与播放条重复入场。


# 第二部分 · Compose 迁移纪要与现状

日期：2026-09-05。当前 XML / Kotlin View UI 已完整替换为 Jetpack Compose，覆盖主壳、资料库、搜索、收藏、播放列表、设置及播放页。迁移以原有已校准实现为视觉与交互基线，保留 Smartisan 资源和本地播放器功能；代码完成与设备验收分别记录。

## 基线与边界

- 用户确认迁移前的实现已完成视觉还原。本次依据当时的代码、资源和既有截图实现，不重新查阅原 APK 或 reverse 材料。
- 保持单 `:app` 模块、namespace、applicationId、Media3 服务、资料库、Room、DataStore 及会话恢复协议。页面消费原有状态、上抛原有事件，不创建第二套播放器或数据源。
- 依赖和 SDK 保持现有工程版本；本次工作范围是 UI 迁移、组件整理、命名和不可达代码/资源清理。
- 保留已有版权和资源来源说明。Compose 页面继续使用自定义 Smartisan 视觉；原版位图、selector 和 9-patch 不因布局技术变化而重新绘制或重新授权。

## 包整理与清理

41 个文件从主壳目录归入对应功能包，`MusicAppShell` 保留跨页面编排；页面、类型和函数移除 `Legacy` / `LegacyPort` 前缀。当前职责与规则见 [UI 架构](ui-architecture.md)。

旧的 40 个布局 XML、生产 UI View 控件、adapter 和 framework shim 已删除，`res/anim` 中退休的 View 动画也已清理。保留的 XML 用于图形、主题、尺寸、颜色和字符串，不再承担页面布局。滚动条的 `declare-styleable` 只读取 framework 主题属性，由 AAPT 生成属性索引。UI 测试中的原生标题栏和 Drawable View 只作为参考对照，不进入生产代码。

资源清理以 main/test/androidTest 的 `R` 引用、Manifest、全部配置下的 XML 传递依赖及生成脚本为根。两轮共删除 256 个不可达资源名，对应 165 个独立文件和 179 条 values 配置声明；夜间生成脚本同步删除 21 条退休规则，保留剩余 153 组映射、6 个深色开关生成源及全部音频素材。清理覆盖同名配置变体，未以 Lint 旧报告作为唯一依据。

动态弹簧库只由标题栏参考测试直接使用，已移入 `androidTestImplementation`；应用对 Compose 间接引入的版本保留约束，确保测试与宿主解析一致。依赖版本未升级。采用 [Gradle 官方依赖约束](https://docs.gradle.org/current/userguide/dependency_constraints.html)（2026-09-05 查阅），约束本身不额外引入模块。

## 真机布局回归修复

2026-09-05，真机出现播放条与导航栏堆叠在屏幕顶部、页面空白的回归。界面树确认列表实际存在，但底栏背景覆盖了内容。根因是 `Modifier.paint(sizeToIntrinsics = false)` 仍参与测量：在宽高均有上界的父约束中，它会将最小尺寸扩到最大尺寸，导致底部自适应高度的容器占满屏幕。

## 二、架构评估（合理性）

**现状**：单模块 `:app`，包分层 `data / diagnostics / platform / playback / ui`，**无 Clean Architecture 的 domain 层、无 UseCase、无依赖注入框架（Hilt）**，大量 `object` 单例 + `SharedPreferences`/DataStore 直连。

**合理的部分**：
- 解码路由用了**策略/门面模式**（`DecodeFrontend` 接口 + `OfficialDecodeFrontend/DirectDecodeFrontend/StreamDecodeFrontend` 三实现 + `FlavorDecodeFrontend` 运行时分派），这是项目里最清晰的一块抽象。
- BASS 全局锁（`BassEngine.nativeLock` + `withLock{}`）是正确且必要的——BASS 非线程安全，这是 1.4.22/1.4.23 闪退根治的核心，**别动**。
- 日志框架 `AppLog`（结构化 `State{}` 帧 + `traceId` + `initiator` 区分 USER/SYSTEM/WATCHDOG + `LogGlossary` 术语对照表）是**远超一般项目水平**的设计。

**不合理/需改进的部分**：
1. **无 domain 层**：播放策略（`OfficialDecodeFrontend.plan`、`PcmDsp.needsPcmPath`）里混着"用户开什么开关→走什么路径"的业务规则，散落在 playback 层各处，改一处策略要翻多个文件。
2. **无 DI**：全靠 `object` 单例 + `context` 手工传参，导致 `MusicTabContent` 30+ 参数、`MusicAppShell` 40+ 状态——这是"牵一发动全身"的结构根源。
3. **设置存储范式混用**（P2，可接受但要知悉边界）：`EngineModeStore/UsbEngineStore/SmartCrossfadeStore/SongListMemoryStore/ColorThemeStore/StatusBarStyleStore` 用 `SharedPreferences+StateFlow`（冷启动同步、首帧不闪），其余约 10 个用 DataStore（异步）。注释已解释这是刻意取舍，合理，但新人接手容易踩。
4. **纯逻辑混入 UI 包**：`ScratchSoundController.kt`（1004 行打碟音效逻辑）、`VinylPopcornSoundController` 是音效引擎，却放在 `ui/playback/` 下，应归 `playback/`。

## 一、音量系统（你这次最火、反复最多的 V1）

### V1 ★ 大播放页音量"剩一格"时点减键降不到 0，要按几十次 —— 【本版 1.4.15 真根因已修】
- **原话**：「音量大播放页的音量只剩一格的时候，无论点多少次减，它都不会降到0，要连续点几十次它才会降到0」`[1][2]`；「刚把音量调到只剩一格的时候，在大播放页按减键，可能不会直接把音量降到0，要多按好几次，但有一部分时候它正常」`[22]`；「无论怎么点减号键都很难让它降到零」`[24]`；「差一格就静音的时候，无论怎么点减键都很难」`[29]`。
- **问题本质（这次才挖到）**：`nudge()` 静音锁调了 `ADJUST_MUTE`，但紧接着 `onVolumeChange(0f)` → `setMusicStreamVolumeFraction(0f)` → `setStreamVolume(0)`，**破坏了静音状态，且 0 档被 UAC 策略弹回 1 档**；回读 `musicStreamVolumeFraction()` 又拿到 1/max，屏幕音量条**又显示剩一格**。形成"静音→弹回一格→再点→再静音→再弹回"死循环。跟步长无关。

## 一、先分两个大类（性质完全不同）

| 大类 | 本质 | 判断依据 |
|---|---|---|
| **投影（Drop Shadow）** | 表达"谁浮在谁上面"的层次 | 有明确的一侧深、向另一侧渐淡；贴在某个实体的边缘外侧 |
| **边缘渐隐（Scroll Fade）** | 表达"列表还能继续滚" | 上下对称出现在可滚动区域两端，不依附任何实体边缘 |

把这两类混在一起谈，是当前最容易出错的地方——`shadow_top` / `shadow_bottom` 看着像阴影，实际是**渐隐**，不该和顶栏投影用同一套规格。

| 底部导航栏 | `tab_bar_shadow.9` | 同样 `scaleY = -1f` 翻转 | `ui/shell/tabs/MusicBottomBar.kt:63-73`，高 14dp，受 `topChromeVisible` 控制 |

**我的结论：应该合并为同一类，但保留两个 drawable 实例。**

理由：
1. **视觉职责完全相同**——都是"把屏幕底部的固定操作区与上方滚动内容分层"，方向一致（向上投）、高度一致（14dp）、翻转手法一致。
2. **两者上下叠放**（小播放栏在底部导航之上），属于同一条"底部 chrome 带"，分类拆开会导致同一条带子被两套规格管理，未来必出不一致。
3. **drawable 不同是合理的**：小播放栏是浮在内容上的浅色半透明条，底部导航是贴屏幕底的实体条，两者底色不同，所以用了两张图。**差异在素材，不在规格**。

**但有一个必须指出的隐患**：两者都向上投 14dp 时，底部导航那层恰好落在小播放栏**背后**——小播放栏有背景色，会把下面那层阴影**完全遮住**。也就是说：小播放栏显示时，底部导航的阴影实际是白画的；只有小播放栏收起（沉浸模式）时才看得到。这不算 bug，但意味着"两道阴影"从来不会同时可见，规格上只需保证**最上面那层**正确即可。

## 9.9 BASS 调用隔离（R76 构建期强制）

**硬规则**：`app/src/main/java` 下，除 `playback/BassEngine.kt` 外，禁止出现任何 BASS native 函数调用。

**实现**：`app/build.gradle.kts` → `verifyBassIsolation`（`group=verification`，挂 `preBuild`，因此
`assembleRelease` / `bundleRelease` 全部会跑）。扫描逻辑：

1. 遍历 `src/main/java/**/*.kt`，跳过 `BassEngine.kt`；
2. 剥块注释（按换行数补回，保证报出的行号是真实行号）与行注释；
3. 两套正则：类名限定 `\b(BASS|BASS_FX|BASSmix|BASSFLAC|BASSOPUS|BASS_DSD|BASSWASAPI|BASSDirect)\s*\.\s*(\w+)\s*\(`
   与裸调用 `\b(BASS_\w+)\s*\(`；
4. 判据：标识符**含小写字母** → 视为函数（native API 全 PascalCase）；全大写 → 常量或纯数据构造，放行；
5. 限定调用已覆盖的区间不再被裸调用重复报；
6. 命中即 `GradleException`，输出 `文件:行号 → 调用`，并写报告到 `build/reports/bass-isolation.txt`。

**为什么这样判**：`BASS_FX.BASS_BFX_BQF_PEAKINGEQ`（常量）与 `BASSmix.BASS_MIXER_NODE(...)`（数据构造）
全大写，必须放行；`BASS_ChannelGetInfo` / `BASS_FX_TempoCreate` / `BASS_Mixer_ChannelRemove` 含小写，必须拦。
用 `\b` 而非 `(?<![\w.])`，是为了让全限定写法 `com.un4seen.bass.BASS.BASS_xxx(...)` 也能被拦到
（早期版本用后者，反向测试发现漏拦，已修）。

**新增 BASS 能力的正确姿势**：在 `BassEngine` 内加 `withLock { if (closed) return … ; BASS.xxx() }` 封装方法，
外部只调封装。不要在业务类里直接 `BASS.*`。

**依据**：`docs/BASS-归因与去留评估.md`（全量归因、能力边界、去留评估、三阶段路线）。

### 分隔栏取色公式（R56-58 / R81-R83）

**根因（实测数值）**：旧 `monetSurfaceContainer()` 返回 `palette.surfaceContainer`，浅色 HSV V=0.96、
深色 V=0.20，与列表背景/原厂 `#F6F6F6` 的亮度差只有 1.5%/5%，肉眼几乎不可见；而且三个方案
在 `palette != null` 分支返回同一个颜色（`if (style == 2) A else A`），M3 主题更是直接
`return fixedSeparatorColor` 连 style 都不看。所谓三方案实际只有一套底色。

**改法**：非 M3 主题改用 `blend(palette.surface, palette.ink, 0.22f 浅 / 0.20f 深)`，实测品牌蓝主题
浅色亮度 90.2%→82.1%（差 8.2%）、深色 20.3%→约 27%（差约 7%），相当于 M3 tone98→tone90 的层级差。
M3 固化主题继续用 `fixedSeparatorColor`。三个方案在 `SectionLetterHeader` 渲染端真正分叉：
0 纯色；1 色块 + `drawBehind` 只画底边 1dp `outlineVariant`（旧 `Modifier.border` 画了四条边）；
2 纵向渐变，终点 = `blend(容器色, surface, 0.35)`，全程带莫奈色相，不再回到 `surface`。

**渐变方向定案**：纵向（从上往下）。分隔栏是通栏横条，横向会左深右浅、右侧融进背景像断了一半。
谷歌 M3 的 Divider 规范只有 1dp `outlineVariant` 线、**没有渐变**；渐变是本 App 自定义可选项，
边界清晰度由方案 1 的底边线保证。

**字母色根因**：`ThemeAccents.palette()` 浅色分支把 `onSurface` 写成 `Color.White`，
违反 M3（浅色 tone10 近黑 / 深色 tone90 近白）。「字母更清晰」开关取 `onSurface`，
于是在浅色分隔栏上打出纯白字。现改为浅 `#1B1B1F` / 深 `#E6E1E5`。

**「独立控制」删除**：旧开关默认 true，且关掉后只要莫奈主开关还开着仍无变化，用户完全无感。

## 9.11 1.4.27 自查补漏：三处「改了但接错」（R85~R87）

> 背景：1.4.26 出包后按用户要求重查「所有任务真的都做了吗」，逐条对着源码复核 R43~R88，
> 查出三处**代码写了但行为错**的地方，全部是 1.4.26 自己引入或 1.4.25 虚报的。

### R85 · 交叉淡化/倒放/变速被 ffmpeg 抢走

**根因**：`plan()` 判定「本首需要 BASS 专有能力」时返回 `STREAM_PCM`，但 1.4.26 把
`openStream()` 改成**一律 ffmpeg 优先**。ffmpeg 一次打开成功就 return，永远落不到 BASS，
`BassCrossfadeMixer` / `BASS_FX_TempoCreate` 根本没被创建。用户开智能过渡听到的是硬切。

**改法**：`openStream()` 按「本首要不要 BASS 专有能力」分两种主次：

```kotlin
val needsBassCapability = BassEngine.isReady && !isBassUnsafe(context, uri) &&
    (SmartCrossfadeStore.currentEnabled() || PcmDsp.needsPcmReverseOrSpeed())
```

- 要 → BASS 优先，ffmpeg 兜底（保证三项能力真能生效）；
- 不要 → ffmpeg 优先，BASS 兜底（保证常规解码不碰 native 崩溃面）。

**教训**：改「主备顺序」时，必须先列出**只有备方能做的事**。ffmpeg 不认识 BASS_FX 的
tempo/pitch 与 BASSmix 的混音，把主备一刀切就等于删功能。

### R86 · dspOwner 在系统直读路径残留

**根因**：`PcmDsp.dspOwner` 只在 BASS 数据源与 `openStream()`（STREAM_PCM）里写。
系统直读（SYSTEM_DIRECT）与转码（TRANSCODE_FLAC）**从不写**，会保留上一条 BASS 流的
`BASS` 标记 → `PcmDspAudioProcessor` 第 97 行按「已由 BASS 处理」全程透传 →
下一首系统直读的 EQ/音效整首失效。

**改法**：`BassPcmDataSource.close()` 把所有权交还 `PCM`（不是 `NONE`），
流的 open/close 成对就能保证状态不残留。

**为什么不写在 `plan()` 里**：`plan()` 会被 `ApeTranscoder.needsTranscode()` 在预取/查询时
重复调用，在里写全局状态会把**正在播的 BASS 流**误标成 PCM，反而造成双施加噪声。
全局状态只能由「流的生命周期」写，不能由「查询函数」写。

### R87 · 硬件音量不支持时 UI 无提示

**根因**：`UsbVolume` 的 `HARDWARE -> if (hardwareSupported) HARDWARE else DIGITAL` 是静默回退。
1.4.25 台账写「UI 明示本设备不支持硬件音量」，实际只做了**零损失**那一档
（`usb_volume_mode_zero_loss_no_hw`），普通「DAC 硬件音量」选项下什么都没有。

**改法**：新增 `usb_volume_mode_hw_unsupported`，在音量模式弹窗里，
当 `current == HARDWARE && !hardwareSupported` 时显示：
「该 DAC 不支持硬件音量：实际会走数字（软件）音量，调音量不会直接改 DAC 芯片。」

## 9.12 1.4.28 全量源码审查（四类问题：逻辑错 / 多此一举 / 挂羊头 / 屎山）

> 背景：用户要求「把所有源码完整看一遍，找出别的模型留下的马虎与漏洞」。
> 257 个 Kotlin 文件、6.5 万行，按模块分三路并行审查 + 逐条源码复核，
> 共确认 60 余条问题，本轮修复 25 处，其余记入台账 R115~R120 并写明不改原因。

### 一、智能过渡的两套实现互相踩

智能过渡（设置页「智能过渡」，内部名 crossfade）有两条路径：

1. **BASS 真双曲混音**：`BassPcmDataSource` 在剩余 ≤ 淡化时长时调
   `BassCrossfadeMixer.activate`，用 BASSmix 把当前曲与下一曲真正混在一起；
2. **音量包络**：`SmartCrossfadeController` 用 `player.volume` 做淡出/淡入。

旧实现两条同时生效：BASS 混音已经在做交叉淡化，包络在最后 `duration/2` 秒又压一次音量，
切歌后还把新曲 `volume=0` 重拉一遍（而新曲开头已被 mixer 播过）→ 用户听到两段式衰减。

修法：`BassCrossfadeQueue` 增加真混音信号（`markRealMixActive/Finished/JustFinished`，
带 120 秒超时保护防泄漏），包络的 `crossfadeOnUserSkip` / `onProgressTick` /
`onTransitionFadeIn` / `onAutoTransition` 四个入口在真混音时全部让位。

### 二、BASS DSP 所有权的单边承诺

`BassPcmDataSource.open()` 无条件 `PcmDsp.dspOwner = BASS`，含义是「DSP 已由我处理，
下游 Processor 必须透传」。但 `BassDspConfig.bassDspEnabled=false` 时
`eqSpecs()` 返回空、`reverb()` 返回 0、`compressor()` 返回 false —— BASS 一个 FX 都没挂。
上游不处理、下游被禁止处理，用户关掉「BASS 接管 DSP」后开 EQ/混响/压限全部静默失效。

修法：`dspOwner = if (BassDspConfig.bassDspEnabled) BASS else PCM`。
所有权必须与「真的挂了效果」一致，不能用一句注释代替状态协商。

### 三、智能过渡的决策链名不副实

- `MorvaniumAnalyzer.outroQuiet` 把「最后一帧三频段能量和」除以「整个窗口帧数」，
  量纲差两个数量级，左边恒接近 0 → 永远判定「结尾安静」。
  改为与 `avgEnergy`（每帧三频段之和的平均）同量纲直接比较。
- `BassCrossfadeMixer.Config.applyTempo` 的唯一调用点硬编码 `false`，
  mixer 里「BPM 对齐」只剩一行日志。**本轮未改**：真变速对齐要用 BASS_FX Tempo
  另建通道，会引入新的句柄生命周期风险，留待单独批次。

### 四、专辑批量删除从入口到实现都是空的

`MainTitleBar` 专辑多选态的删除按钮 `onClick = {}`，全工程没有任何专辑删除实现，
`selectedAlbumIds` 只被选中和清空。点击毫无反应，且无法退出多选（只能返回键）。

修法：
- `AlbumModels.albumGroupingIdOf(MediaItem)`：与专辑页分组**同一口径**的分组键入口
  （旧 `AlbumIdExtraKey` 是 private，外部想复用只能复制一份规则）；
- `MusicAppShell.requestAlbumDeleteConfirmation`：按分组键收集选中专辑下全部可见歌曲，
  复用 `SongDeleteConfirmOverlay` + `MediaStore` 系统删除链路 —— 两次确认，不会静默删文件。

### 五、返回键两套实现与状态残留

系统返回认 `albumJumpOrigin`/`artistJumpOrigin` 回来源页；标题栏返回箭头直接
`closeAlbumDetail()`，既不认来源、也不清 origin。后果：
从歌曲页「查看专辑」进去，标题栏返回落到专辑列表、系统返回落到歌曲页；
更糟的是残留的 origin 会让**下一次**从专辑页进详情后的返回被弹回歌曲页。

修法：抽出 `backFromAlbumDetail()` / `backFromArtistDetail()`，两处统一调用；
跨页返回时同时清 `selectedAlbumId`/`selectedArtistTarget`；`closeAlbumDetail()` 内部清 origin。

### 六、记忆式首页失效

`LaunchedEffect(sortKey)` 在**首次组合**就 `clearScrollIndex`，而
`LaunchedEffect(active)` 随后才读位置，读到的已被清空 → 冷启动永远回顶部
（只有从别的页切回来时才碰巧有效）。另外 `saved < rows.size` 在资料库未加载时
直接跳过却仍置 `restoreDone=true`，不会重试。

修法：首次组合不清位置（用 `lastSortKey` 区分「首次」与「真的换排序」）；
恢复逻辑拆成独立 effect，key 加 `rows.size`，等数据到位再恢复。

### 七、主题可读性两处硬伤

- `themedPressedTextColor` 取 `onSurfaceTint`（浅色恒 V=0.97 近白），
  而按下底色是 `primaryContainer`（浅色 V=0.90 高饱和亮色）→ 白字压亮底，
  实测 1.6~2.0:1，按住任意行标题就看不见。改用 `onSurface`（浅近黑/深近白）。
- `onPrimaryContainer` 默认值 = `primaryContainer`（注释却写「默认=onSurface」，
  注释与实现相反）。深色模式下暗色图标落 `#282b30` 底栏，实测 1.2~2.8:1。
  两处 `palette()` 与 `MonetColors.monetize()` 按明暗显式给可读的主题色。

## 9.13 1.4.29 背景莫奈化统一入口与 JNI 产物校验（R121~R132）

### 9.13.1 一个入口：`libraryTexture(pageDeep)`

位置：`ui/library/SmartisanLibraryComponents.kt`

```kotlin
@Composable
internal fun Modifier.libraryTexture(
    @DrawableRes resource: Int = R.drawable.account_background,
    pageDeep: Boolean = false,
): Modifier
```

行为：
1. 背景莫奈化关（且逐元素取色关）→ 只铺原厂纹理，零改动；
2. 开 → `drawBehind` 先画纹理图，再叠 `rememberMonetBlankTint(pageDeep)` 的线性渐变。

`rememberMonetBlankTint`（`ui/theme/MonetSurface.kt`）：
- 浅色：`blend(primaryContainer, ink, 0.42f)` 作为色雾；正常档 alpha 0.12，暗档 0.20；
- 深色：`blend(primaryContainer, onSurface, 0.30f)` 作为雾；正常档 0.08，暗档 0.05（暗档提亮更少 = 相对更暗）；
- 渐变三色 alpha 依次 ×0.86、×0.72，**首尾都有色，不衰减到透明**（旧版径向渐变到边缘透明，等于只有屏幕中间有色）。

页面归属：
- 更多页、设置页四个文件（`SettingsPages` / `SettingsPage` 内层 / `ThemeSettingsPage` / `ColorThemeSettingsPage`）传 `pageDeep = true`；
- 其余库页、搜索页、播放队列、根背景传默认 `false`；
- 全局开关 `MonetStore.deepBackgroundEnabled` 打开时，`pageDeep` 被强制为 true（`deep = pageDeep || globalDeep`）。

### 9.13.2 两套「叠渐变」不要混用
